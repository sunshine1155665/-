# ADR-0012：在线层与能力层分离（云主机试用）

> 相关：[运维](../branches/ops.md) · [架构](../overview/architecture.md) · [路线图](../overview/roadmap.md) · 代码：`config/cloud.toml`、`deploy/linux/`

## 背景

现在「她在不在线」和「她能不能唱歌」绑在同一台 Windows 笔记本上：

- 笔记本睡眠 / Windows 更新重启 / 断电 → QQ 掉线、Web 打不开、主动消息全停；
- 反过来，只要她想唱歌或拍照，8GB 显卡就要独占，TTS 必须让位。

`config/remote.toml` 从很早就写着 *thin client; heavy services run on the main machine*，
但这个 profile 从未真正投产。2026-10-29 拿到一台 2C2G 的 3 个月试用云主机，正好可以
把这条假设拿去验收。

本 ADR 记录的是**启动这次验证的决策**，不是「云端常驻」的最终结论。

## 问题

要不要把「在线」从「能力」里拆出来？

| 层 | 是否必须和 GPU 在一起 |
|---|---|
| 接入（QQ / Web） | 否 |
| 编排（`runtime.py`） | 否 |
| 记忆（SQLite + FTS） | 否（实测 39MB，见下） |
| 能力（TTS / SoulX / ComfyUI） | **是** |
| 模型（LLM） | 否，本来就是远端 API |

结论是只有「能力层」必须留家。

## 决策

**启动 3 个月试用，按 B 方案（在线层常驻）验证，不立即采纳。**

1. 云主机跑 `fatfish` 的接入 + 编排 + 记忆，profile 用 `cloud`（`config/cloud.toml`，
   merge 在 `low.toml` 之上，只关 GPU 能力）。
2. 家里的 GPU 服务**只做无状态能力**：TTS(9880)、bge(9881)、ComfyUI(8188)、SoulX。
3. **SQLite 单写者**：云为主库时，家里那份只读/备份，不允许两边同时写。
4. 家里没开时允许降级为纯文字——这是产品决定，不是缺陷。
5. 试用结束必须给出「采纳 / 否决」的结论并回填本文，不允许悬空。

## 依据（2026-10-29 实测）

真实库只读副本、`memory_items=56`、`db=2.5MB`、hash 256 维：

| 阶段 | 常驻 RSS |
|---|---|
| Python 启动 | 15.6 MB |
| 打开 Database | 18.7 MB |
| `MemoryService()` | 26.3 MB |
| **全部服务（含贴纸索引）** | **39.0 MB** |

检索 2–4ms。结论：**记忆库不是内存瓶颈**。

真正的瓶颈是向量服务：

| 项 | 内存 |
|---|---|
| `import torch`（cu128 wheel） | 483 MB |
| `import transformers` | 517 MB |
| bge-base-zh 权重（磁盘 391MB） | ≈900 MB 合计 |

所以 2C2G 上不跑 bge（`sticker.embedding_backend = "hash"`）。代价：库里存的 768 维
向量与 256 维查询宽度不符，**余弦相似度恒为 0**（启动时有 `_check_stored_width` 警告），
打分只剩 `0.25×关键词 + 0.30×意图`：自发阈值 0.50 基本够不着，表情包大幅变少；
「明确点图」阈值 0.20 仍可用。语义记忆召回不受影响，因为 `low` 本来就用 hash 256 维。

流量（按 20GB/月 的免费额度对照）：文字 + LLM 60–250MB、语音 30–150MB、图片 30–90MB、
Web 60–300MB、备份 60–150MB，**典型 0.5–1GB/月/人，上限按 3GB 估**。额度用不到 15%。

成本：2C2G 经济型 e ¥0.123/h，3 个月 24h ≈ ¥266，落在 300 元试用额度内。

## 备选与否决理由

| 方案 | 结论 | 理由 |
|---|---|---|
| A. 仅灾备（家里主、云接管） | 否决 | 要「谁主谁从」的切换机制，SQLite 双写风险最高，收益最小 |
| **B. 在线层常驻** | **本次验证** | 单写者、与 `remote` profile 同构、故障面最小 |
| C. 全量上云（含 GPU） | 否决 | g6.xlarge ≈ $588/月；模型重下、本机路径要全部重配、扫码登录全要重做 |
| D. 不动，只加固本机 | 保留 | 成本 0；若试用证明掉线 <1 次/周，这就是答案 |
| E. 共用一个云账号（与朋友） | 否决 | 腾讯云账号协议 2.2.1 明确禁止借用；免费额度按人发，共号反而少一份 |

## 后果

**正面**

- 她 24h 在线不再依赖笔记本是否醒着；主动消息、唤醒、夜间归档都有稳定载体。
- 8GB 显卡的互斥只影响「唱歌/拍照」，不再影响「回消息」。
- `remote` profile 第一次被真正使用，它的设计假设得到验证或证伪。

**负面 / 风险**

- 多一套部署面：`config/cloud.toml` 进漂移快照，`deploy/linux/` 要跟版本走。
- 多一条回切路径：云挂了怎么办必须写脚本，不能临场想。
- 隐私边界变化：正式库明文落在机房；`secret_notes` 与私聊记录都在里面。
- 语音多一跳（家 → 云 → QQ），延迟 +50–100ms；家里断网时语音不可用。
- 免费/低价机随时可能改规则（Oracle 2026-06 就把 A1 从 4C24G 砍到 2C12G）。

## 验收判据（90 天）

| 指标 | 采纳阈值 | 否决阈值 |
|---|---|---|
| 云端 7 天掉线次数 | ≤1 | >2 |
| 内存峰值 | <1.4G / 2G | 频繁 OOM |
| 月流量 | <5GB | 超 20GB 额度 |
| QQ 重扫码 | ≤1 次/月 | ≥1 次/周 |
| 语音端到端延迟 | <+1.5s | 用户可感知 |
| 维护负担 | 每周 <15 分钟 | 每周 >1 小时 |
